## 2. Prompt Injection Architecture & LLM Comprehension Strategy

### 2.1 Design Objectives for LLM System Prompts
When a financial fraud analyst queries Gemini or requests an automated case briefing / SAR filing, the LLM must have access to **unambiguous ground truth** about why each rule triggered. Without encyclopedia context, LLMs frequently hallucinate vague generic fraud summaries.

To optimize LLM attention and token utilization, the injected encyclopedia context follows these principles:
1. **Two-Tier Information Density**:
   - **Tier 1: High-Density Markdown Table**: At-a-glance index of triggered rules, evaluated metrics, severity points, and one-line summaries. Allows the LLM to quickly anchor the severity and breadth of the violation.
   - **Tier 2: Deep Algorithmic Breakdowns**: Individual sections per triggered rule detailing the exact mathematical formula, evaluated parameter values, modus operandi typology, and regulatory compliance rationale.
2. **Mathematical Precision with Plain-English Clarity**:
   - Mathematical formulas are expressed in standard LaTeX / mathematical notation ($DMV = 100 \cdot (0.4D + 0.6V)$) alongside plain-text computational definitions.
   - Plain-English rationales explicitly answer: *"Why is this behavior abnormal?"* and *"What criminal modus operandi does this indicate?"*
3. **Token Efficiency & Anti-Drift Anchoring**:
   - Context is compact (~150–250 tokens per triggered rule).
   - Strict boundaries are maintained so the LLM cannot confuse heuristic rules with raw transaction facts.

### 2.2 Standard Injected Markdown Structure

The prompt context string generated by `build_case_encyclopedia_context(evaluated_rules, metrics)` is formatted as follows:

```markdown
### 📚 SAMPATI ENCYCLOPEDIA ALGORITHMIC KNOWLEDGE BASE
The following algorithmic detection rules, mathematical thresholds, and forensic typologies were evaluated for this case:

| Rule Code | Rule Name | Evaluated Metric | Severity | Detection Summary |
|---|---|---|---|---|
| `DMV_RAPID_DRAIN` | Dead Money Velocity | `82.5/100` (Drain: 96%) | CRITICAL (40 pts) | Extended dormancy (45d) followed by near-total balance dissipation within 1 hour |
| `R_SIM_DEVICE_MISMATCH` | SIM / Device Mismatch | `Device: a1b2c3d4` | HIGH (30 pts) | Known account active on unfamiliar device hardware indicating SIM-swap or takeover |
| `PASS_THROUGH_CONDUIT` | Pass-Through Conduit | `Ratio: 94%` (₹75k/₹80k) | HIGH (30 pts) | Entity immediately forwards ≥90% of incoming funds to downstream nodes |

---

#### 1. `DMV_RAPID_DRAIN` — Dead Money Velocity
- **Mathematical Formula**: $DMV = 100 \cdot (0.40 \cdot D + 0.60 \cdot V) \times M$
  - Dormancy Index: $D = \min(1.0, \Delta t_{\text{dormant}} / 30\text{ days})$
  - Burst Velocity Index: $V = 0.50 \cdot (\text{Outflow} / \text{Inflow}) + 0.30 \cdot (\text{TxnCount}_{1h} / 4) + 0.20 \cdot (\text{Amount} / 30000)$
  - Multiplier $M = 1.0 + 0.5 \cdot (D \cdot V)$ if $D \ge 0.5 \land V \ge 0.4$, else $1.0$
- **Evaluated Metric**: `82.5/100` (Account dormant for 45 days; drained 96% of ₹80,000 inflow within 42 minutes).
- **Forensic Rationale**: Mule account signature pattern. Legitimate operational accounts maintain continuous baseline velocity. Criminal cash-out networks recruit dormant "sleeper" accounts to rapidly funnel illicit proceeds before freezing orders can be issued.
- **Regulatory Typology**: Layered Mule Laundering / Rapid Pass-Through Account Draining (RBI Master Direction on Digital Payment Security Controls).

#### 2. `R_SIM_DEVICE_MISMATCH` — SIM / Device Identity Mismatch
- **Mathematical Formula**: $\text{Mismatch} = (\text{Payer}_{\text{Device}} \ne \text{Hist}_{\text{Device}} \land \text{Payer}_{\text{SIM}} == \text{Hist}_{\text{SIM}}) \lor (\text{Payer}_{\text{Device}} == \text{Hist}_{\text{Device}} \land \text{Payer}_{\text{SIM}} \ne \text{Hist}_{\text{SIM}})$
- **Evaluated Metric**: New device ID `a1b2c3d4...` bound to known SIM IMSI `8991...`
- **Forensic Rationale**: Indicates unauthorized account takeover via SIM-swap or device cloning. Legitimate UPI payers exhibit consistent SIM-hardware pairing.
- **Regulatory Typology**: Account Takeover / SIM-Swap Fraud (Cyber Crime Prevention Protocol).

#### 3. `PASS_THROUGH_CONDUIT` — Pass-Through Relay Conduit
- **Mathematical Formula**: $\text{Ratio} = \frac{\text{Outflow}_{\text{window}}}{\text{Inflow}_{\text{window}}} \ge 0.90 \quad \text{and} \quad \text{TxnAmount} \ge 0.50 \cdot \text{Inflow}_{\text{window}} \quad \text{and} \quad \text{AccountAge} < 30\text{ days}$
- **Evaluated Metric**: Forwarding ratio: 94% (₹75,000 outflow against ₹80,000 inflow in 60-minute window).
- **Forensic Rationale**: Intermediary relay node in a multi-hop mule pipeline designed to obscure transaction trails across PSP boundaries.
- **Regulatory Typology**: Pass-Through Layering Conduit (FIU-IND Red Flag Indicator).
```

## 4. Metric Interpolation Engine Specification

### 4.1 Interface Contract
```python
def get_rule_explanation(
    rule_code: str,
    metric_value: Optional[Union[float, int, str]] = None,
    context: Optional[Dict[str, Any]] = None,
) -> Dict[str, Any]:
    """Retrieve indexed explanation with dynamic metric interpolation.
    
    Returns:
        dict with keys:
            - rule_code: Canonical rule identifier (str)
            - name: Human-readable rule title (str)
            - mathematical_definition: Concise mathematical formula string (str)
            - plain_english_explanation: Contextual explanation with interpolated metrics (str)
            - severity: Threat level ('CRITICAL' | 'HIGH' | 'MEDIUM' | 'LOW' | 'INFO') (str)
            - default_points: Risk score points contribution (int)
            - regulatory_typology: Relevant FIU-IND / RBI compliance typology category (str)
    """

def build_case_encyclopedia_context(
    evaluated_rules: List[Union[str, Dict[str, Any], RuleHit]],
    metrics: Optional[Dict[str, Any]] = None,
) -> str:
    """Build formatted markdown knowledge base context for system prompt injection.
    
    Args:
        evaluated_rules: List of rule codes, dicts ({'code': '...', 'detail': '...'}),
                         or RuleHit objects.
        metrics: Optional dictionary containing runtime evaluation metrics
                 (e.g. {'dmv_score': 82.5, 'adaptive_score': 0.92, 'amount': 75000, ...})
                 
    Returns:
        Formatted markdown string with high-density summary table and
        detailed per-rule algorithmic breakdowns.
    """
```

### 4.2 Interpolation Resolution Rules
1. **Scalar `metric_value` Binding**:
   - If `metric_value=0.92` for `BEHAVIORAL_ANOMALY`:  
     `"Evaluated Metric: Anomaly Score = 0.92/1.00 (Z-score: 3.68σ above baseline mean)."`
   - If `metric_value=82.5` for `DMV_RAPID_DRAIN`:  
     `"Evaluated Metric: DMV Score = 82.5/100 (Critical velocity drain)."`
   - If `metric_value=49990.0` for `LIMIT_SKIRTING`:  
     `"Evaluated Metric: Amount ₹49,990.00 sits ₹10 (0.02%) below ₹50,000 regulatory caution threshold."`
2. **Context Dictionary Resolution**:
   - If `context={"inflow": 80000, "outflow": 75000, "ratio": 0.9375, "window_min": 45}` for `PASS_THROUGH_CONDUIT`:  
     `"Evaluated Metric: Forwarded ₹75,000 (93.8%) of ₹80,000 incoming funds within 45 minutes."`
   - If `context={"speed_kmh": 1240.5, "distance_km": 620, "time_min": 30}` for `R_IMPOSSIBLE_TRAVEL`:  
     `"Evaluated Metric: Travel speed: 1,240.5 km/h over 620 km in 30.0 min (exceeds 1000 km/h physical limit)."`
3. **Graceful Fallbacks for Edge Cases**:
   - `None`, `NaN`, `Inf`, or missing metric: Fall back to canonical baseline threshold statement (e.g., `"Threshold exceeded based on runtime evaluation parameters"`).
   - Negative values or out-of-range: Cleanly clamped or formatted without throwing exceptions.
   - String values (e.g. `"0.92"`, `"₹75,000"`): Safely converted and formatted.
